# ФАЗА 5 — БЕЗОПАСНОСТЬ (готовность к аудиту)

> Сначала вставь общий контекст из `prompts/00-context.md`, затем — задание ниже.
> Предусловие: Фазы 1–4 завершены.

## Задание

### 5.1 Rate limiting и защита от перебора PIN (КРИТИЧНО — 4 цифры = всего 10 000 комбинаций)
- На все PIN-эндпоинты (регистрация PIN, вход/гейт попыток, восстановление сертификата) введи
  серверный rate-limit по IP: например не более 5 попыток за 10 минут, затем экспоненциальная
  задержка/временная блокировка.
- Дополнительно — блокировка по «неудачным попыткам восстановления» с одного IP.
- Ответы с одинаковой формулировкой и сопоставимым временем (без утечки по времени).
- Реализуй лимитер устойчиво (в БД или Upstash/Vercel KV), НЕ в памяти процесса — иначе он
  обнуляется при холодном старте serverless.

### 5.2 Эндпоинты прокторинга (/api/proctoring/event, /heartbeat)
- Проверь наличие api-guard и усиль: allowlist типов событий, лимиты размера тела и длины
  строковых полей, rate-limit по `attemptId`/IP.
- GET-лог не публичный: закрой админ-ключом или отдавай только агрегаты.
- Убедись, что `integrity_score` считается на сервере и клиентское значение не авторитетно.

### 5.3 Общие меры под аудит
- Заголовки безопасности в `next.config`: Content-Security-Policy (без `unsafe-eval`),
  X-Frame-Options / frame-ancestors (учти, что эмбед должен работать — разреши нужные origin),
  X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin,
  Strict-Transport-Security, Permissions-Policy (camera/microphone только где нужно).
- Все секреты — только серверные переменные окружения (`SERVER_PEPPER`, `RESULTS_API_KEY`,
  `DATABASE_URL`). Ни один секрет не имеет префикса `NEXT_PUBLIC_` и не попадает в бандл.
- Админ-сессия: httpOnly + Secure + SameSite=Strict cookie; сравнение ключа — constant-time
  (`timingSafeEqual`); fail-closed при незаданном `RESULTS_API_KEY`.
- Все серверные экшены валидируют вход (zod или существующий `lib/validation.ts`): формат PIN,
  длины строк, диапазон `rating` 1–5. Никакого доверия клиенту.
- Никакого `dangerouslySetInnerHTML`. Проверь вывод пользовательского текста (комментарии
  отзывов) в админке.
- SQL — только через Drizzle/параметризованные запросы (никакой конкатенации строк).
- Логи: не логируй PIN, `pin_lookup`, ключи, тело запросов с секретами.
- Проверь, что E2E-режим (`lib/e2e.ts`, `NEXT_PUBLIC_E2E_TEST_MODE`) НЕ включается в продакшене
  и не раскрывает правильные ответы при `NODE_ENV=production`.
- Убедись, что удалены остатки email-функциональности (`sendResultEmail`, `RESEND_*`), если
  письма больше не отправляются — иначе это лишняя поверхность атаки и хранение ПДн.

## Критерий готовности фазы
- Перебор PIN блокируется устойчивым (не in-memory) лимитером.
- Заголовки безопасности выставлены, эмбед не сломан.
- Секретов с `NEXT_PUBLIC_` нет; админ-сессия и API fail-closed.
- Отчёт: изменённые файлы + список мер безопасности.
